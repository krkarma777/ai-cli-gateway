# v0.1 Release and SDK Onboarding Design

**Date:** 2026-08-04

**Status:** Approved for implementation as the first milestone of the
2026-08-04 roadmap

## Summary

AI CLI Gateway will become installable as a verified GitHub Release and will
prove its advertised API subset through the official OpenAI Python and
JavaScript SDKs.

This milestone does not broaden the HTTP API. It packages the existing five
tested target tuples, publishes checksums, an SPDX SBOM, and signed GitHub build
provenance, adds a single-provider Codex configuration example, and
runs both SDK examples against the real gateway executable and a deterministic
fake Codex CLI.

The release and SDK checks are separate from provider credentials. They never
install, log in to, or invoke a real Codex, Claude, or Gemini CLI.

## Milestone boundary

This is the first independently testable subproject in the approved roadmap.
It covers:

- tag-driven multi-platform GitHub Releases;
- deterministic archives and build metadata;
- SHA-256 checksums;
- an SPDX JSON SBOM generated from the staged release binaries;
- signed build provenance covering every published asset, including the SBOM;
- official OpenAI Python and JavaScript SDK examples;
- a black-box SDK contract test using the real gateway and fake CLI; and
- a release-first README Quick Start.

The following approved roadmap items remain separate subprojects with their own
designs and plans:

- configuration generation and more actionable Doctor output;
- provider compatibility automation and live validation;
- liveness, readiness, metrics, and service-manager coverage;
- client-owned tool/function calling; and
- true provider-backed SSE streaming.

Splitting these units keeps each plan independently releasable and prevents
distribution work from changing the final-output API contract.

## Goals

- A strict `vMAJOR.MINOR.PATCH` tag on a commit already contained in `main`
  produces a draft GitHub Release and publishes it only after every verification
  step passes.
- Release archives exist for the five target tuples already cross-built by CI:
  Linux amd64/arm64, macOS amd64/arm64, and Windows amd64.
- `ai-cli-gateway version` in a release build reports the exact tag, source
  commit, and normalized UTC source-commit timestamp.
- Archives contain only the executable and fixed public documentation/config
  files, with stable names, order, permissions, ownership metadata, and
  timestamps.
- Consumers can verify every release asset with `SHA256SUMS` and GitHub's signed
  build-provenance attestation.
- An SPDX JSON SBOM describes the union found in the five staged static
  executables and is itself checksummed and published.
- The official OpenAI Python and JavaScript SDKs can list models and create one
  non-streaming text response through the gateway's documented subset.
- Default Go development remains independent of Python, Node, real provider
  CLIs, provider credentials, and paid inference.
- README users encounter installation and a short successful request path
  before the detailed architecture and contract reference.

## Non-goals

- Homebrew, Scoop, Winget, apt, rpm, Docker, or an additional package-manager
  repository.
- `curl | sh`, a privileged installer, automatic PATH modification, or automatic
  service installation.
- Installing or authenticating provider CLIs.
- Discovering, copying, modifying, or storing provider authentication material.
- API additions, streaming, tool calls, sessions, or stored responses.
- Widening provider version ranges.
- Claiming full OpenAI SDK or OpenAI API compatibility.
- Reproducibility across different Go toolchains or GitHub runner generations.
  The narrower guarantee is deterministic packaging for one source commit,
  Go 1.26.5, and the pinned release tooling.

## Considered approaches

### 1. GoReleaser publishes the release

GoReleaser is familiar and concise, but it combines cross-build, archive,
checksum, and GitHub publication authority in one third-party tool. Its config
would be harder for this repository's closed security tests to exercise at the
archive boundary.

### 2. Inline shell builds and archives

GNU tar, gzip, and zip can produce the desired files on Ubuntu. This is smaller
initially, but deterministic behavior would depend on runner utilities and would
not be directly executable by the native macOS and Windows test suites.

### 3. Small Go archive packer plus a split GitHub workflow — selected

The workflow performs explicit five-target `go build` commands. A repository
internal Go package creates tar.gz/zip archives and checksum manifests using the
standard library. Its path validation, normalized metadata, fixed contents, and
determinism are executed and tested on its supported Linux and macOS packaging
hosts. Windows remains a release artifact target and compile target; the
internal releasepack tool is not executed on Windows.

The workflow separates package/attestation authority from publication authority.
This adds a small amount of repository-owned release code but keeps publication
transparent and minimizes third-party release logic.

## Release authorization and workflow

### Trigger and verification

`.github/workflows/release.yml` is triggered only by tags matching `v*.*.*`.
The package job must then reject everything except this closed regular
expression:

```text
^v(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)\.(0|[1-9][0-9]*)$
```

Prerelease and build suffixes are deliberately excluded from v0.1 automation.
The workflow resolves annotated and lightweight tags with
`git rev-parse "${TAG}^{commit}"`, fetches `main`, and requires the resolved
commit to be an ancestor of `origin/main`.

`ci.yml` gains a `workflow_call` trigger without changing its ordinary push and
pull-request behavior. The release workflow's first job calls that workflow with
read-only contents permission. Packaging cannot start unless the existing
Linux, macOS, Windows, race, fake CLI integration, trimmed-path, lint, and build
checks pass.

The release concurrency key is repository plus tag, and in-progress release runs
are never canceled automatically.

Repository tag rules should prevent ordinary contributors from creating,
moving, or deleting `v*` tags. Release immutability should be enabled before the
first public tag. These repository settings are part of release commissioning,
not a runtime dependency.

### Job permissions

The reusable verification workflow retains `contents: read` only.

The package job receives only:

```text
contents: read
id-token: write
attestations: write
```

It has no release-publication permission. It checks out the exact tag, builds and
packages assets, creates attestations, and transfers one short-lived internal
workflow artifact.

The read-only asset-verification job receives only:

```text
contents: read
attestations: read
```

It downloads the package job's immutable internal artifact by artifact ID,
re-verifies its checksums and signed build provenance, and performs no release
mutation. The publish job cannot start unless this job succeeds.

The publish job receives only `contents: write`. It downloads the same internal
artifact by ID, re-verifies its checksums before invoking any release mutation,
creates a draft release, uploads all assets without overwrite, and finally
changes the draft to public. Attestation verification does not occur in this
write-authorized job.
No job runs on `pull_request_target`, uses a repository secret, invokes a
provider CLI, or tolerates a failed step.

GitHub's standard `GITHUB_TOKEN` is exposed to the GitHub CLI through the
documented `GH_TOKEN` environment variable only in the read-only attestation
verification step and the publish step. The repository hygiene scanner will
recognize the exact `${{ github.token }}` workflow expression as a non-secret
placeholder; no literal credential is committed.

### Build metadata

The resolved tag commit is the sole metadata source:

```text
Version = exact vMAJOR.MINOR.PATCH tag
Commit  = 40-character lowercase tag commit SHA
Date    = tag commit timestamp normalized to UTC as YYYY-MM-DDTHH:MM:SSZ
```

All five builds use Go 1.26.5 with:

```text
CGO_ENABLED=0
-trimpath
-buildvcs=false
-mod=readonly
-s -w
```

The workflow injects the three `internal/buildinfo` variables with separate
`-X` linker assignments. Client input, environment credentials, or provider
paths never participate in release arguments.

A host Linux/amd64 binary smoke test must print exactly:

```text
ai-cli-gateway <tag> (<commit>, <date>)
```

Every target is also inspected with `go version -m` to confirm its GOOS, GOARCH,
module path, and clean module dependency metadata.

## Archive contract

The releasepack `archives` subcommand accepts only:

- an absolute repository root containing the expected module declaration;
- an absolute staging root with the exact five target subdirectories;
- an absolute, initially absent or empty output directory that is private to
  the invoking account;
- the validated tag; and
- the normalized source timestamp.

The later `sbom` and `checksums` subcommands accept that same private output
root only after independently revalidating its authority and the exact expected
nonempty asset membership for their phase.

It rejects symlinks, non-regular source files, an unexpected target, a missing
target, unsafe output paths, existing output assets, and paths that escape an
accepted root.

The repository, staging, and output roots are absolute, clean, non-symlink, and
pairwise disjoint. The v0.1 release packer executes on Linux or macOS; Windows
is an archive and compile target, not a supported release-packaging host. A
newly created output root is descriptor-chmodded and verified to have exact mode
`0700`. For `archives`, an existing output root is accepted only when it is
empty; every phase requires the existing root to be owned by the invoking
effective UID and already have exact mode `0700`. On every releasepack
invocation, the shared root validator independently checks the
output root or its existing parent plus every ancestor: each must be a real
non-symlink directory owned by the effective UID or root, and a group/other
writable ancestor is accepted only when it has the sticky bit. This prevents an
unrelated account from replacing the private root through a writable parent.
The caller owns that directory as an exclusive transaction workspace and must
not let another process under the same OS identity mutate the root or its
entries until the releasepack subcommand returns. The workflow and local dry
run create it below an account-private temporary root.

Concurrent mutation by another process running with the same OS identity is
outside the v0.1 threat model. Such a process already has equivalent authority
to alter the repository, staging binaries, or release process. Portable Go and
the supported host APIs do not provide an atomic "unlink this pathname only if
it still has this file identity" operation, so pre-remove identity checks are
defense in depth rather than a claim of protection against a same-credential
racer. Publication still uses a no-clobber hard link, accepts a final path as
owned only after proving it identifies the completed temporary file, and never
overwrites a pre-existing or unexpectedly replaced final path.

Failure cleanup attempts to remove only paths still proven owned. Recoverable
one-shot lifecycle failures must leave no owned asset. Persistent close, unlink,
or directory-removal failure can make complete cleanup impossible even without
a racer; in that case the invocation returns only `archive_failure`, returns no
assets, and the whole private transaction root is tainted and must be discarded
rather than reused. The CLI, workflow, and dry run stop immediately on that
nonzero result, so no SBOM, checksum, attestation, transfer, or upload consumes a
tainted root. The project does not claim guaranteed deletion when the filesystem
itself persistently refuses cleanup.

Archive creation, SBOM finalization, and checksum generation each revalidate the
same root set independently; later subcommands do not trust an earlier process
invocation to have established it.

The asset names omit the tag's leading `v`:

```text
ai-cli-gateway_0.1.0_linux_amd64.tar.gz
ai-cli-gateway_0.1.0_linux_arm64.tar.gz
ai-cli-gateway_0.1.0_darwin_amd64.tar.gz
ai-cli-gateway_0.1.0_darwin_arm64.tar.gz
ai-cli-gateway_0.1.0_windows_amd64.zip
ai-cli-gateway_0.1.0_sbom.spdx.json
SHA256SUMS
```

Each platform archive has one fixed top-level directory matching the archive
base name. Every archive contains:

```text
ai-cli-gateway or ai-cli-gateway.exe
README.md
LICENSE
THIRD_PARTY_NOTICES.md
config.example.toml
examples/config/codex.example.toml
examples/openai-sdk/python/main.py
examples/openai-sdk/python/requirements.txt
examples/openai-sdk/python/requirements.lock
examples/openai-sdk/javascript/main.mjs
examples/openai-sdk/javascript/package.json
examples/openai-sdk/javascript/package-lock.json
```

Linux archives additionally contain
`deploy/systemd/ai-cli-gateway.service`. The service example remains linked from
README for other installation paths, but is not bundled into macOS or Windows
archives where it cannot be used.

Entries are sorted lexically. Directories use mode `0755`, Unix executables use
`0755`, the Windows executable and public files use `0644`, uid/gid are zero,
user/group names are empty, gzip carries no original filename, and every entry
uses the normalized source timestamp. ZIP comments are empty. ZIP metadata may
contain only the deterministic extended-timestamp field emitted by Go's standard
library for that normalized timestamp; unrelated or source-derived extra fields
are forbidden. The source timestamp must fit both ZIP's MS-DOS date range and
the extended timestamp's unsigned 32-bit Unix range, and archive-reader tests
inspect both local and central headers.

`SHA256SUMS` is generated after the SPDX file. It contains exactly six sorted
binary-mode records: five archives and the SBOM. It never includes itself or the
GitHub-internal transfer artifact.

## SBOM and signed provenance

The package job invokes a commit-pinned `anchore/sbom-action` with a fixed Syft
version against the directory containing the five staged static executables.
The action step fixes Syft's missing-name policy to `drop` and missing-version
policy to `stub` and accepts no ambient/user config, so the local main module is
always serialized as `UNKNOWN` rather than depending on runner configuration.
Automatic workflow-artifact and release upload are disabled. Syft writes one raw
SPDX JSON file outside the release-output directory. Syft 1.50.0 describes a
directory scan with path-derived document/root-package data and already emits
binary file records, so the raw document is validation input rather than an
output template. The repository-owned release packer parses it, compares its Go
module packages with all five staged binaries through Go's `debug/buildinfo`,
and constructs a closed collection-level SPDX projection. That projection has
fixed document metadata, exactly the validated module packages, five
deterministic relative file records with staged SHA-256 values, and fixed
relationships from the document to files and from files to the modules they
contain. Raw path-derived document, root-package, file, and relationship nodes
are never copied.

The validator requires SPDX 2.3, `CC0-1.0`, `SPDXRef-DOCUMENT`, a nonempty package
set, a nonempty relationship set, and the exact Syft 1.50.0 tool creator. Raw
SPDX IDs must be unique and every expected module package instance must be
reachable from the raw document without a dangling relationship. Syft emits
root-relative target file names and may emit one package instance per target for
the same module tuple. Each target file's exact `OTHER` relationship with the
fixed `evident-by: indicates the package's existence is evident by the given
file` comment must bind it to exactly the build-info module set plus the standard
library derived from that binary's `GoVersion`; the final projection then
deduplicates identical tuples. Module packages must have an exact module-path
name and canonical exact Go purl; substring matching is forbidden. The locally
built main module has build-info version `(devel)` and must appear as
`versionInfo: UNKNOWN` with no purl version. Dependencies must match both
`versionInfo` and purl version exactly. The standard-library package must match
the full `goMAJOR.MINOR.PATCH` build-info version and Syft's purl version with
the leading `go` removed. Replacement modules are rejected for this fixed release rather than
guessed across Syft replacement semantics.

Syft also emits one redundant binary-classifier package only for the Windows
executable. The validator permits exactly its pinned name/version/no-purl shape,
one Windows evidence edge, one root containment edge, and no other relationship;
it validates and discards that classifier. Every other unexpected evidence
package fails closed. The canonical collection retains the deduplicated main,
dependency, and standard-library packages.

The canonical document name, namespace, creation timestamp, package IDs, file
IDs, fields, order, and relationships are generated from the validated tag,
normalized source timestamp, module tuples, target paths, and hashes. It contains
no raw root package and exactly five file records covering the target tuples.
Their hashes must match staged executable bytes. Absolute staging, workspace,
runner-home, or developer-home paths are forbidden in the final JSON by
construction and by a final recursive scan. A checked-in, path-redacted fixture
preserves the structural output of a real five-binary Syft 1.50.0 scan so changes
to its root package, preexisting files, and relationship layout cannot silently
break finalization. Unit fixtures also cover empty/partial catalogs, one omitted
target, wrong hashes, wrong versions, purl prefix collisions, missing module
relationships, duplicate IDs, and private-path leakage.

The resulting document is explicitly a collection-level SBOM for all five staged
target binaries. It is not attached as though the same predicate described each
individual archive, because that would overstate the relationship between one
platform archive and the other four binaries.

After checksums are independently re-read and verified, commit-pinned
`actions/attest@v4` creates one signed build-provenance attestation covering the
five archives, collection-level SPDX file, and `SHA256SUMS`.

For each of the seven subjects, the read-only asset-verification job calls
`gh attestation verify` with predicate type
`https://slsa.dev/provenance/v1`, the canonical
`github.com/krkarma777/ai-cli-gateway/.github/workflows/release.yml` signer
workflow, `--repo krkarma777/ai-cli-gateway`, the resolved tag commit as source
digest, and `refs/tags/<tag>` as source ref. It also re-verifies
`SHA256SUMS`. Only after that job succeeds can the separate publish job start;
the publish job rechecks the same immutable artifact's checksums before its first
mutation.

A failed build, packaging check, SBOM step, attestation, transfer, read-only
verification, publication checksum check, or upload prevents a public release.
Before creating a draft, the publish job uses a fixed GitHub GraphQL
`release(tagName:)` query. Creation is permitted only when the authenticated
query succeeds and its release field is exactly `null`; an existing release,
authentication or authorization failure, network or server error, timeout, or
unparseable response stops before mutation. It then uses `gh release create` with
`--verify-tag`, an explicit tag-derived title, generated notes, and `--draft`.
Immediately before draft creation and again immediately before changing the
draft to public, the job resolves the live remote tag through the GitHub REST
API. It accepts a lightweight commit ref or exactly one annotated-tag layer,
rejects nested/malformed objects, and requires the peeled commit to remain the
package job's validated main commit. A moved tag leaves the draft non-public.
It never resumes, deletes, or overwrites an existing draft automatically. If an
upload partially fails, an operator must inspect and explicitly remove the
non-public draft before rerunning; the workflow reports the fixed
`release_already_exists` category until that recovery is complete.

GitHub documents that artifact attestations are signed Sigstore claims binding
artifacts to their workflow, repository, commit, and event. They establish
provenance, not that the binary is vulnerability-free:

- https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations
- https://docs.github.com/en/actions/concepts/security/artifact-attestations

The repository will document both checksum and `gh attestation verify` commands.

## Official SDK contract

### Examples

The checked-in examples use exact SDK pins:

- Python `openai==2.53.0`, with Python 3.12 in CI and a separate resolved CI
  requirements lock;
- JavaScript `openai@6.48.0` (`"openai": "6.48.0"` in `package.json`),
  with Node 24 in CI and a committed lockfile.

The JavaScript example is native ESM rather than TypeScript requiring a build
tool. The same official package supplies the JavaScript/TypeScript SDK.

Both examples require these environment variables:

```text
AI_CLI_GATEWAY_BASE_URL   # includes /v1
AI_CLI_GATEWAY_API_KEY
AI_CLI_GATEWAY_MODEL
AI_CLI_GATEWAY_TIMEOUT_SECONDS   # optional integer, 1..300; defaults to 300
```

They use a bounded user-facing request timeout of up to 300 seconds and disable
SDK retries. The deterministic contract harness sets the optional timeout to
exactly five seconds; direct release users may keep the 300-second default or
choose a smaller positive integer. Both clients call `models.list()`, then call
`responses.create()` with only the gateway's supported fields:

```json
{
  "model": "<configured alias>",
  "instructions": "SDK contract instruction.",
  "input": "SDK contract input.",
  "text": {"format": {"type": "text"}},
  "stream": false,
  "store": false,
  "tools": [],
  "tool_choice": "none"
}
```

No example enables SDK debug logging. Missing environment variables fail locally
with the missing variable name but never echo a value.

The Python SDK's `base_url`, Responses client, and public request ID are
documented by the official repository:

- https://github.com/openai/openai-python

The JavaScript SDK's `baseURL`, Responses client, retry, and timeout options are
documented by its official repository:

- https://github.com/openai/openai-node

### Black-box harness

The fake CLI gains one `codex-ready` mode and a dedicated `fake-codex-cli`
fixture command that selects that mode internally. The real gateway config uses
the dedicated fixture as its executable with no `prefix_args`; arbitrary Unix
prefix arguments remain forbidden. The fixture recognizes the real Codex
adapter's closed probe commands and returns:

- version `codex-cli 0.146.0`;
- every required exec/help option;
- every required hardening feature in the disabled state;
- authenticated login status;
- an eligible closed Doctor JSON report; and
- `SDK_GATEWAY_OK\n` for an ordinary final-output execution.

Unknown or malformed command shapes in this mode fail closed. The fake never
reads provider credentials or performs network access.

`scripts/sdk-contract.sh` receives the prepared virtual-environment Python
executable, the Node executable, and an absolute path to a runner-temporary copy
of the checked-in JavaScript entrypoint. Copying the JavaScript sample beside its
runner-temporary `node_modules` is required because native ESM resolves packages
from the importing file's location rather than from an unrelated install prefix.
The shell entrypoint validates its repository location and executes a
repository-owned Go SDK-contract runner with argv, not a shell command string.
The Go runner owns port allocation, child lifecycle, bounded log capture, and
cleanup; those dependencies, including readiness timers, are injectable in unit
tests. The supported runner hosts are macOS for local execution and Linux for
local execution and CI. Windows remains compile-tested but `Run` returns
`unsupported_platform` before entropy, temporary-root creation, or process
startup. From a validated repository root, the harness:

1. validates the Python and Node arguments as absolute paths, records the alias
   leaf and resolved-target identities, and requires both paths to have
   non-symlink directory ancestors owned by root or the effective UID; a
   group/other-writable ancestor is accepted only when sticky, exactly matching
   the private-root authority rule; targets must be non-group/other-writable regular
   executables; the JavaScript entrypoint must itself be an absolute,
   non-group/other-writable, non-symlink regular file whose identity is retained;
   immediately before every use the runner re-resolves and proves the same
   identities, while still executing the original Python/Node aliases so
   virtual-environment and launcher behavior is preserved;
2. creates one private temporary root as a sibling of the repository checkout,
   descriptor-chmods and verifies it as exact `0700`, and retains its identity
   until exact-root cleanup; the root parent follows the same root-or-effective-
   UID, non-symlink, non-writable-ancestor rule as the release transaction root;
3. builds the real gateway and dedicated fake Codex fixture into that root;
4. asks the supplied Python runtime to bind `127.0.0.1:0`, records the assigned
   concrete port, closes that probe socket, and writes a test-only single-Codex
   configuration with the fake CLI and alias `codex-sdk-test`; the test config
   uses bounded shutdown values and the harness grace exceeds its declared
   gateway shutdown timeout;
5. generates the synthetic gateway key from exactly 32 CSPRNG bytes encoded as
   64 lowercase hexadecimal ASCII characters, then starts the real gateway under
   an empty environment containing only a minimal PATH, private HOME, and that
   key;
6. polls authenticated `GET /v1/models` with injected 100 ms timers and a hard
   injected five-second deadline; one validated lifecycle-policy value owns all
   timing: poll 100 ms, readiness five seconds, probe one second, gateway grace
   ten seconds, helper grace one second, registry protocol two seconds, and
   registry cleanup two seconds. `runWithSystem` passes the applicable duration
   into every Build, AllocatePort, RunClient, registry-construction, timer, and
   cleanup call. Any nonpositive or overflowing policy field fails before temp
   creation, entropy, timers, or processes. The real system contains no
   independent lifecycle duration or fallback, while repeated unit tests inject
   fake timers and short positive grace;
7. on early exit or a retryable readiness failure, stops and reaps the gateway
   before repeating port allocation, fresh runtime/config creation, and startup
   up to eight total attempts; cancellation stops and reaps but never retries;
   this bounded retry closes the bind-zero-then-close race without changing the
   production listener contract;
8. runs both SDK examples with only the four gateway variables plus their
   runtime's required minimal environment;
9. always terminates the final attempt's gateway process group and joins its
   single `Cmd.Wait`, then finalizes the root-scoped test-fixture process registry
   exactly once as described below; and
10. removes the temporary root only when every started helper, gateway, and
    registered fixture group is proven absent and the pathname still names the
    retained non-symlink directory identity. A replacement or an unsafe cleanup
    result preserves the private root and fails closed.

All external commands used for build, port allocation, gateway startup, and SDK
execution run without a shell in a new Unix process group. Context cancellation
sends TERM to the negative group, escalates to KILL after a bounded grace, joins
the one owned `Cmd.Wait`, and verifies that the non-session-escaping group is
absent. Cleanup ownership transfers immediately after each successful process
start. Constructors are transactional. A nonnil value with nil error transfers
one ordinary owner; nil plus a plain error certifies complete rollback with no
retained artifact, goroutine, process, descriptor, or timer. Nil plus a
cleanup-safety error that proves absence also certifies rollback but preserves
cleanup-error precedence. Post-allocation failure or uncertainty returns the
nonnil recovery owner together with a cleanup-safety error, so the caller can
perform terminal cleanup; nil plus an error claiming live/unverified retained
resources is an invalid constructor result and fails closed. A nil value with a
nil error is likewise invalid and fails closed. Primary validation, readiness,
SDK, or cancellation categories survive only if gateway shutdown, fixture
cleanup, helper-process cleanup, and exact-root removal all succeed; cleanup
failure takes precedence and prevents another startup attempt. Remaining cleanup
steps are still attempted when they are safe.

Gateway stdout/stderr is never emitted directly. Each attempt has a distinct
mutex-protected in-memory scanner that retains at most 64 KiB, keeps draining and
scanning the entire stream after overflow, and detects forbidden values across
write boundaries with a rolling suffix. Overflow, scanner failure, or a secret,
request, response, executable path, config path, or runtime-root match produces
only a fixed failure category. No raw gateway log file is created. Only the two
already validated fixed SDK success markers reach the harness output.

Unit tests force a first-attempt address collision, eight-attempt exhaustion,
early child exit, cancellation, and cleanup failure through the runner's
dependencies. The black-box CI invocation still uses real loopback sockets and
real gateway/fake-CLI child processes.

A Unix integration fixture also blocks a real provider process after spawning an
ignore-TERM descendant. The provider is deliberately in a different process
group from the gateway, so killing the gateway group alone is not containment.
Before the first readiness attempt the harness creates one root-scoped,
exact-mode-`0600`, bounded named-pipe registry adjacent to the test-owned fixture.
It remains active across all eight possible gateway readiness attempts and is
finalized exactly once during terminal cleanup, never while retiring a retryable
attempt. On entering its final handler the
fixture first registers its provider PID/PGID, then starts the descendant in the
same group, waits for the descendant's TERM-handler readiness handshake without
owning a second timer, and registers the descendant before declaring the fixture
ready. Missing, malformed,
partial, duplicate, oversized, or timed-out registration fails closed; if the
descendant was started, the fixture kills and waits it before returning.

An untouched registry with zero bytes and zero records is valid for the ordinary
immediate fake CLI, a pre-protocol terminal failure, or exhausted readiness
attempts. The ordinary runner never calls `Ready`. Calling `Ready` is an
integration-only operation that atomically arms the requirement for a complete
protocol and returns a channel closed only after both valid records; observing
the first protocol byte also arms the same requirement. The first arming event
starts the registry's policy-supplied two-second protocol timer, which wholly
bounds provider registration, descendant readiness, and descendant registration.
No readiness duration is transported to the slow child through argv,
environment, file, or another hidden default. Once armed, absent, partial,
missing-continuation, malformed, duplicate, oversized, or timed-out completion is
a cleanup failure. The slow integration calls and waits for `Ready` with its own
bounded context; timing out that wait cancels the run and terminal registry
finalization still fails closed even if zero bytes arrived.

After joining the terminal gateway, the harness finalizes this registry and
receives both an error and an explicit `SafeToRemove` result. If a registered
provider group remains, it sends TERM and then KILL, if needed, and requires the
registered group and PIDs to be absent. Root removal is attempted only when
every helper/gateway result and the registry result prove `SafeToRemove`. A
non-nil cleanup error with proven absence still permits `RemoveExact`, while any
live or unverified process/group retains the private root, closes its retained
handle if possible, and returns only `sdk_contract_cleanup_failed`. The fixed
public error contains no path; the report/README tells the local operator that a
private `.sdk-contract-*` recovery root may require manual inspection and
cleanup. `RemoveExact` consumes and closes its retained handle on every return,
including identity mismatch or filesystem failure; the retain-without-removal
path uses a separate idempotent Close operation.

Cleanup results admit exactly four interpretations. `{SafeToRemove:true,
Err:nil}` is clean. `{true, nonnil}` proves absence but is still a cleanup error:
`RemoveExact` is attempted and the public category is cleanup_failed. `{false,
nonnil}` means a live or unverified group: skip removal, close the lease, and
retain the root. `{false,nil}` is invalid and is normalized to a fixed internal
cleanup error with the same skip-remove/close-lease behavior. Any nonnil or
normalized error wins the public category; no underlying value or root path is
published.

On graceful gateway shutdown the gateway owns provider reaping. If the gateway
must be killed, the harness can only terminate registered non-child fixture
processes and observe their disappearance; it does not claim to have called
`wait` on non-children. This is a fail-closed test-fixture registry, not generic
containment of a provider that deliberately calls `setsid` or otherwise escapes
its inherited process group. Same-credential mutation between the last identity
check and exec or removal is likewise outside the v0.1 threat model.

The `sdk-contract` command derives its runner context from
`signal.NotifyContext`; macOS/Linux observe Interrupt and SIGTERM and always stop
notification. Therefore cancellation during build, allocation, readiness, SDK
execution, or shutdown enters the same bounded cleanup state machine.

Both SDK clients assert:

- exactly one `codex-sdk-test` model record;
- a completed `response` for `codex-sdk-test`;
- one completed assistant message with one `output_text` item;
- `output_text == "SDK_GATEWAY_OK\n"`;
- the echoed supported request fields and fixed empty/null fields;
- semantic `resp_`, `msg_`, and `req_` ID prefixes; and
- `completed_at >= created_at`.

This proves SDK parsing and transport compatibility only for the documented
subset. It does not claim SDK-wide compatibility.

### CI isolation

CI adds one Linux-only `sdk-contract` job. It installs the Python lock into a
mode-`0700` root created by the runner's temporary-directory facility. Local
macOS/Linux instructions create the same private root with `mktemp -d` below the
host's `${TMPDIR:-/tmp}` and do not assume `/private/tmp`. CI copies `main.mjs`,
`package.json`, and `package-lock.json` into a runner-temporary JavaScript
workspace and runs
`npm ci --ignore-scripts` there. It passes that copied entrypoint to the harness,
which builds the gateway and fake CLI outside the source tree and runs both
checked-in examples.

Python and Node are not Go module dependencies, root project runtimes, or
requirements for ordinary `go test ./...`. Native gateway process containment
continues to be tested by the existing OS-specific jobs.

## Quick Start and configuration example

README gains an early Quick Start that covers:

1. selecting the release asset for the host tuple;
2. downloading the archive and `SHA256SUMS`;
3. selecting exactly that archive's one manifest record, verifying its SHA-256,
   and optionally verifying the GitHub attestation;
4. extracting to an unprivileged user path;
5. copying `examples/config/codex.example.toml` to `config.toml`;
6. replacing the Codex executable, Codex config-home, and private runtime-root
   placeholders;
7. replacing the model placeholder with a Codex model the user's authenticated
   CLI account can access;
8. generating an optional gateway Bearer key into an owner-only file outside the
   release tree and explicitly loading it in each serve/request terminal;
9. running `doctor`, then `serve`; and
10. sending one curl or official SDK request.

The key file is treated as data, never sourced or displayed; each shell validates
its exact 64-character lowercase-hex form before export. POSIX uses mode `0600`
inside a `0700` directory, and PowerShell removes inherited ACLs and grants only
the current user read/write. The Quick Start never applies a six-subject manifest check to a directory that
contains only one subject. The download, SHA-256 verification, extraction,
executable placement, environment variable, and path-substitution commands are

placeholder syntax unchanged. A

and runs the real config decoder. POSIX CI performs the corresponding

## Error model

The runtime HTTP error catalog is unchanged.

Release tooling returns a nonzero process status with a closed, non-sensitive
category for invalid usage, invalid tag, unsafe path, missing input, build
failure, archive failure, checksum failure, SBOM failure, attestation failure,
or publication failure. Nil has no error category; unknown internal failures map
to one fixed internal category. It does not print arbitrary file contents,
environment values, or tool output beyond a bounded diagnostic.

SDK examples treat a non-2xx gateway response as an SDK exception and exit
nonzero. The contract harness reports only the exception class/status and its own
fixed phase name; it does not enable HTTP body or header debug logging.
If `sdk_contract_cleanup_failed` retains a private recovery root because process
absence or root identity was not proven, command output still reveals no path or
underlying error. README instructs a local operator to ensure no recorded
contract process remains, then inspect and remove only the exact owner-only
`.sdk-contract-*` sibling; it never recommends deleting a parent or glob.

## Security boundary

- Release authority starts at a protected exact SemVer tag contained in `main`.
- Only the final publish job has `contents: write`, and it depends on a separate
  read-only asset-verification job.
- Only the package job can request an OIDC identity and write attestations.
- Every third-party release action is pinned to a full commit SHA and documented
  with its release version; Syft is also fixed to an exact version.
- The read-only job verifies signed provenance and transferred bytes; the
  publication job re-verifies bytes without executing repository code before
  upload.
- No provider credentials or GitHub long-lived secrets are used.
- Release outputs are created outside the repository and are never committed.
- The release output directory and its ancestor authority are validated as an
  invoking-account-private, exact-mode-`0700`, single-process transaction
  workspace; same-credential concurrent mutation is explicitly outside the
  v0.1 threat model.
- Archives accept no user-controlled paths or names.
- SDK tests use a synthetic gateway key and an empty inherited environment.
- SDK helper, gateway, and client commands are group-canceled and waited on
  macOS/Linux; the blocking integration fixture additionally registers its
  separate provider group for fail-closed termination after forced gateway
  death. Deliberate `setsid` escape is outside this fixture-only guarantee.
- SDK path and temporary-root identities are revalidated at their use/removal
  boundaries. Same-credential concurrent mutation remains outside the v0.1
  threat model, and no atomic compare-and-exec or compare-and-delete guarantee
  is claimed.
- Prompts, outputs, schemas, credentials, provider stderr, full argv, and
  authentication identities remain absent from logs.
- Provider installation and use remain the user's responsibility under the
  provider's applicable terms.

## Test strategy and acceptance criteria

### Release packer

- RED/GREEN unit tests cover exact target membership, archive names/layout,
  normalized modes/times, sorted entries, checksum sorting, and invalid input.
- Real archive readers inspect every tar.gz and zip rather than checking source
  text, and compare every regular entry's payload bytes with its fixed source.
- Identical staging bytes and source time packaged twice produce byte-identical
  archives and checksum records.
- Symlink, missing-file, extra-target, nonempty-output, non-`0700` output,
  foreign-owner output, unsafe-parent-authority, and root-escape fixtures fail
  before any asset is published.
- Restrictive-umask creation tests prove a newly created output root is
  descriptor-chmodded and verified to exact mode `0700`; cleanup-fault tests
  distinguish recoverable one-shot failures from persistent failures that taint
  and quarantine the whole unpublished transaction root.
- SPDX fixtures prove the final collection document contains exactly five
  hash-matching relative binary records, a nonempty module/dependency union
  reachable through valid relationships, and no private filesystem paths.

### Workflow contracts

- Repository security tests parse `release.yml` separately from the existing CI
  contract and verify triggers, the exact verify/package/asset-verification/
  publish jobs, split permissions, bounded timeouts, five builds, metadata
  injection, checksum verification at both permission boundaries, constrained
  provenance verification including the fixed repository scope, immutable
  internal artifact transfer, `--verify-tag`, explicit noninteractive release
  metadata, draft-first publication, fail-closed successful-null-only
  existing-release handling, and absence of overwrite/bypass behavior.
- The ordinary CI workflow remains read-only and continues to run on push and
  pull request; its updated exact job set includes the SDK contract job.
- A local release-packaging dry run exercises the actual packer with synthetic
  executables.

### SDK boundary

- Fake CLI tests watch `codex-ready` fail before its implementation, then cover
  every real readiness command and final execution.
- Both official SDK examples run against the real gateway process in CI and must
  independently validate the complete supported response shape.
- Missing-key and wrong-key cases fail without disclosing the synthetic value.
- Gateway shutdown is awaited and the test runtime is empty afterward.
- The bounded startup retry is exercised by occupying the first selected port;
  exhaustion fails and still leaves no child process or runtime artifact.
- Fake-timer tests cover the five-second readiness boundary without wall-clock
  delay, use an injected short lifecycle-grace policy, and exercise cancellation
  before and after every root, registry, gateway, readiness, Python, and
  JavaScript ownership transition. The real forced-kill integration runs once
  separately with production grace values rather than inside `-count=10`.
- Unix tests force graceful and KILL gateway shutdown, cancellation of every
  helper process group, and a separately grouped provider with an ignore-TERM
  descendant. One root-scoped registry survives all readiness retries and is
  finalized only during terminal cleanup; zero-record ordinary/exhausted runs
  succeed, while begun partial/malformed/overflow/timeout protocols fail closed.
  Registered processes are absent before exact-root removal is accepted.
- Cleanup-safety tests prove that an error with all groups absent still attempts
  `RemoveExact`, while a live or unverified helper, gateway, or fixture group
  closes the lease without removing the private root and returns only
  `sdk_contract_cleanup_failed` without its path.
- Table tests cover all four cleanup-result states, including normalization of
  invalid `{SafeToRemove:false, Err:nil}`. Duration-plumbing tests record every
  exact lifecycle-policy value received by Build, AllocatePort, RunClient,
  registry construction, StopAndWait, StopAndVerify, and timer creation, and
  prove the real system has no second policy/default. The slow fixture receives
  no duration transport because registry protocol grace wholly bounds its
  descendant handshake.
- Replacement tests cover the owned root, Python/Node alias and resolved target,
  and JavaScript leaf. Restrictive-umask tests prove exact `0700` directories and
  `0600` config/registry files. Log tests include split secrets and secrets after
  the 64 KiB retention limit while proving the entire stream is drained.
- Constructor fault tests cover every post-allocation step: a plain error leaves
  no retained artifact/goroutine/process, and rollback uncertainty is promoted
  to cleanup failure with root removal marked unsafe. `RemoveExact` closes its
  retained handle on success and every failure path.
- Command tests deliver Unix SIGTERM and observe runner-context cancellation.
  Windows cross-compiles and returns `unsupported_platform` before creating a
  temporary root.
